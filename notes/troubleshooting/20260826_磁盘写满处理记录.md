## 二、 处理过程

### 1. 应急恢复

- **查看磁盘整体使用情况：**
  ```bash
  df -h
  # 输出示例：/dev/sda1  /data  98%

- **定位大文件/大目录：**

  bash

  ```
  cd /data
  du -sh * | sort -rh | head -5
  ```

- **发现罪魁祸首：**
  发现 `/data/logs/app/catalina.out` 大小达到 **17G**。

- **清理日志文件（重定向清空，避免进程卡死）：**

  bash

  ```
  > /data/logs/app/catalina.out
  ```

- **检查空间是否释放：**

  bash

  ```
  df -h
  ```

- **若清理后空间未释放，检查被删除但未释放句柄的文件：**

  bash

  ```
  lsof | grep deleted
  # 找到对应 PID 后重启服务释放句柄
  systemctl restart [服务名]
  ```

## 三、 常用定位命令清单

| 排查目的               | 命令                                          | 说明                       |
| :--------------------- | :-------------------------------------------- | :------------------------- |
| 查看各目录占用         | `du -sh * | sort -rh`                         | 快速找出最大子目录         |
| 查找大于1G的文件       | `find / -type f -size +1G -exec ls -lh {} \;` | 精准定位大文件路径         |
| 清理正在写的日志       | `> filename.log`                              | 推荐用重定向，避免进程卡死 |
| 检查 inode 是否爆满    | `df -i`                                       | 排查小文件过多导致无法写入 |
| 查看被删但未释放的文件 | `lsof | grep -i deleted`                      | 查找"幽灵文件"释放空间     |

## 四、 根因分析

- **直接原因：** 应用的日志级别被设置为 `DEBUG` 模式，且未配置日志滚动（Log Rotation）。
- **根本原因：** 上周排查接口 Bug 时将 `logback.xml` 改为 DEBUG，未及时恢复，且缺少对该目录的磁盘监控。

------

## 五、 永久规避措施

- 将该服务器日志目录（`/data/logs`）添加到监控系统，阈值设为 80% 预警。
- 修改应用日志配置文件，增加滚动策略（按天切割，保留最近 7 天）。
- 建立日志清理定时任务（Cron job），每天凌晨清理超过 7 天的归档日志。
- 制定上线检查清单，确保发布后日志级别恢复为 INFO/WARN。

------

## 六、 经验教训

1. 线上环境严禁长期开启 DEBUG 日志，上线后必须改回 INFO/WARN。
2. 磁盘告警阈值应设为 80%，提前干预，避免等到 95% 才处理。
